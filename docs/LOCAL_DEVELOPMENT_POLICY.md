# سياسة التنفيذ المحلي وتأجيل التكاملات الخارجية

## النطاق الحالي
- الوكيل ينفذ الكود والاختبارات والبيانات التجريبية داخل workspace/الكمبيوتر المحلي الذي يعمل عليه. لا ينشر تطبيقًا ولا يشغل خدمات سحابية كجزء من التنفيذ الحالي.
- قاعدة البيانات أثناء التطوير محلية: PostgreSQL محلي (يفضل Docker Compose إذا كان متاحًا، وإلا تثبيت محلي موثق). صمم SQL/migrations بأكبر قدر عملي من التوافق مع PostgreSQL/Supabase Postgres مستقبلًا. لا تضع بيانات حقيقية.
- GitHub هو مستودع مصدر/نسخ ملفات عند طلب المالك، وليس runtime أو قاعدة بيانات. لا ترفع أسرارًا أو dumps أو بيانات شخصية. لا تنشر على Vercel أو GitHub Pages الآن.
- التكامل مع Supabase السحابي مؤجل بالكامل: لا تنشئ مشروعًا أو اتصالًا أو مفاتيح أو migrations سحابية أو Auth/Storage/Edge Functions مستضافة. لا تطلب credentials.
- أي ميزة تتطلب Supabase أو مزودًا خارجيًا (بوابة دفع، InstaPay آلي، بريد/SMS، شحن، AI API، analytics خارجي) تُترك غير مفعلة، ويسجل ما يمنع إتمامها في `DEFERRED_EXTERNAL_INTEGRATIONS.md` مع task/السبب/المتطلبات/الاختبار المطلوب.
- لا تتظاهر mocks/local adapters بأنها تكامل حقيقي. استخدم بيانات محلية معلّمة، وواجهات adapter مع خطأ واضح/flag تعطيل عند غياب المزود.

## المصادقة والصلاحيات محليًا
يمكن تنفيذ تسجيل دخول محلي محدود للتطوير إذا لم يتطلب خدمة Supabase: تخزين محلي آمن مناسب، كلمات مرور مجزأة، جلسات آمنة، حماية CSRF/rate limit بالقدر الملائم. لا تستخدم حسابات تجريبية ضعيفة أو أسرار ثابتة. إذا كان نطاق Auth الآمن خارج المهمة، اترك التدفق معطلًا وسجله بدل إنشاء حماية شكلية. قواعد التفويض والتحقق الخادمي تظل مطلوبة محليًا؛ لا يعتبر ذلك بديلًا عن Supabase Auth/RLS للإنتاج.

## إتمام المهمة
لا تُعلّم مهمة تتضمن جزءًا سحابيًا `COMPLETED` لمجرد إتمام الجزء المحلي؛ اذكر الجزء المحلي المنجز والجزء المؤجل، واستخدم `NEEDS_REVIEW` أو `BLOCKED` بحسب معيارها. لا تغير المرجع الأساسي أو المتطلبات لأجل الالتفاف على التكامل.

## استئناف التكامل لاحقًا
عند طلب المالك صراحةً، تُراجع قائمة المؤجل، ثم يُنشأ Supabase project/بيئات ومفاتيح عبر قناة آمنة، وتنفذ migrations وسياسات RLS واختبارات وصول واستعادة منفصلة قبل أي إطلاق.
